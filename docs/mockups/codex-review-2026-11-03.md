## P0：運用開始前に必ず修正

### 1. お客様の申込が店舗に届かない【①④】

- **行番号：** 515–534、708–723
- **問題：** `window.claude` がない環境では必ず localStorage を使います。申込処理も `data.unshift(r); localSave();` のみです。お客様の端末とスタッフの端末でデータは共有されません。
- **直し方：** 現在の構成を維持するなら、公開フォームの受付機能を停止し、電話など実際に受け付けられる窓口へ案内してください。文言例：  
  **「このフォームからお申し込み内容を送信することはできません。ご予約のご相談は、お電話（011-596-7770）で承ります。」**  
  Web受付を実現するには、店舗が受信できる外部フォームサービスなどへの接続が必要です。

### 2. メール送信・PDF添付をしていないのに「送信しました」と記録する【①②④】

- **行番号：** 413、715、831–836、866–882、912、939–944
- **問題：** 受付メール、確認メール、請求書メール、再送のいずれにも送信処理がありません。請求書PDFの生成もありません。それでも状態が「共有済み」「請求済み」に進み、送信成功の履歴が残ります。
- **直し方：** 手動運用に合わせ、作成と送信確認を分離します。
  - 「確認メールを送信」→ **「メール本文をコピー」**
  - 別途 **「メールソフトで送信済みにする」** を設け、スタッフが実際に送信した後だけ状態を変更
  - 「請求書を作成して送信」→ **「請求書を作成」**
  - 「請求書を再送」→ 実際の再送手段を実装するまで削除
  - 履歴は **「スタッフがメールの送信完了を記録」** とし、`auto:false` にする

### 3. Googleカレンダーの登録・更新・削除が実行されない【①②④】

- **行番号：** 731–735、815–826、910–911、925
- **問題：** 確定時に生成する `evt_...` はランダム文字列です。Googleへの登録処理はありません。「Googleカレンダーで開く」も既存予定の表示ではなく、新規作成用URLです。繰り返し利用すると別予定を作成できます。
- **直し方：** 「日程を確定」と **「Googleカレンダーの予定作成画面を開く」** を分離します。保存の成否はこのリンクでは取得できないため、手動登録の確認欄を設けてください。「自動登録」「更新」「削除」の履歴を生成せず、取消時には **「カレンダーの予定も手動で削除してください」** と表示します。

### 4. 保存失敗を無視して成功表示する【①④】

- **行番号：** 516–519、675–676、716–723、909
- **問題：** `localSave()` が例外を握りつぶします。容量超過などで保存に失敗しても、登録完了・申込完了を表示し、入力内容をリセットします。再読み込みすると変更が失われます。
- **直し方：** 保存関数から例外を返し、保存成功後にだけメモリ上のデータ・画面・状態を更新します。例えば新規登録は次の順序にします。

  ```js
  function persist(nextData) {
    localStorage.setItem(STORE_KEY, JSON.stringify(nextData));
  }

  const nextData = [r, ...data];
  try {
    persist(nextData);
    data = nextData;
    formNew.reset();
    show('detail', r.id);
  } catch {
    // 入力を残したまま、画面内に表示する
    showSaveError('保存できませんでした。入力内容は残っています。');
  }
  ```

  詳細変更も `r` を直接変更せず、複製した予約を保存してから反映してください。

### 5. ワンクリックで実データを全削除できる【①④】

- **行番号：** 274、521–528、604
- **問題：** 「サンプルデータに戻す」を押すと、確認・バックアップなしで全予約をサンプルに置き換えます。
- **直し方：** 本番ではボタンとイベントハンドラーを削除してください。デモが必要なら、本番とは別の保存キー・別画面に分離します。

### 6. 初回起動・読み込み失敗時にサンプル予約を実データとして表示する【①④】

- **行番号：** 476–506、515、629
- **問題：** 保存データがない場合だけでなく、JSON解析失敗時にも `seed()` を返します。データ破損がサンプル表示に隠されます。配列なら内容を検証しないため、`[null]` などでは一覧描画が例外になります。
- **直し方：** 未保存なら空配列、解析・構造検証に失敗した場合は復旧画面にします。破損した元データを上書きせず、退避できるようにしてください。`status`、日付、数値、状態に必要な `calendar / actual / invoice` などを検証します。

### 7. バックアップ・復元がない【④】

- **行番号：** 474、509–550、全体
- **問題：** 永続保存先はブラウザ内の1キーだけです。ブラウザデータ削除・端末故障に備えるエクスポート／インポート機能がありません。
- **直し方：** バージョン付きJSONのダウンロードと、構造検証付き復元を追加します。

  ```js
  {
    schemaVersion: 1,
    exportedAt: new Date().toISOString(),
    reservations: data
  }
  ```

  復元前には件数・対象期間を表示し、現データもバックアップします。運用画面に **「このブラウザだけに保存されています。閉店時にバックアップしてください」** と常時表示してください。

### 8. 複数タブで予約を消し合う【①④】

- **行番号：** 510、516、534、675、717
- **問題：** 起動時に読み込んだ配列全体を毎回保存し、`storage` イベントや競合検知がありません。A・Bの2タブを開き、Aで予約追加後にBで別予約を追加すると、Bの古い配列がAの追加分を消します。
- **直し方：** 保存データにリビジョンを持たせ、保存前の比較と排他処理を行います。`storage` イベントでは編集中の変更を上書きせず、競合を表示してください。明日までの暫定運用は **管理用端末・ブラウザ・タブを1つに限定**する必要があります。

### 9. 請求書の発行者・登録番号・振込先が仮置き【②④】

- **行番号：** 473、895、903
- **問題：** `[発行者名（会社名）]`、`[登録番号 T0000000000000]`、`[銀行名]` などを請求書にそのまま出力します。451行の説明にある設定画面も実装されていません。
- **直し方：** 確認済みの発行者情報・振込先を設定するまで請求書作成を無効化します。登録番号が未設定の場合、仮番号を出力せず、表示の要否を確定してください。

## P1：予約・請求の正確性に影響

### 10. 人数・金額・時刻の入力検証が不足【①】

- **行番号：** 280、343、648、672、698–700、850–863、923–935
- **問題：**
  - `novalidate` のため、HTMLの `min`・`required`・`step` は送信を止めません。
  - スタッフ登録では人数を検証していません。
  - お客様フォームは `!f.people` のみで、負数・小数を通します。
  - 実績の人数0は `||1` で黙って1人に変換されます。
  - 予約編集には入力検証がありません。
  - 空時刻の `hoursBetween('', '')` は `NaN` になり、`<=0` では検出できません。
- **直し方：** 登録・編集・実績保存に共通の検証を使います。

  ```js
  const validPeople = Number.isSafeInteger(people) && people >= 1;
  const timePattern = /^(?:[01]\d|2[0-3]):[0-5]\d$/;
  const validTime =
    timePattern.test(start) &&
    timePattern.test(end) &&
    hoursBetween(start, end) > 0;
  ```

  延長単位・追加金額も非負の安全な整数で検証し、空欄を暗黙に補完しないでください。実際に、軽食等と同じ計算経路で「パーティ・人数−10・1時間」は **−14,600円**になります。

### 11. 同じ時間帯の予約を重複確定できる【①④】

- **行番号：** 669–676、708–723、910、923–926
- **問題：** 新規登録・日程確定・日程変更のいずれにも既存予約との重複チェックがありません。
- **直し方：** 同じ会場・日付で、他の確定予約との重なりを確認します。

  ```js
  other.id !== r.id &&
  other.date === r.date &&
  r.start < other.end &&
  other.start < r.end
  ```

  仮予約同士は警告、確定予約との重複は確定を止めるなど、運用を明示してください。localStorageでは別端末の予約を検査できない点も解消が必要です。

### 12. 過去日・営業時間外でも申込・確定ができる【①】

- **行番号：** 562、656–661、689、698–700、726、823–826、910
- **問題：** 過去日や営業時間外は警告表示だけで、申込・確定を止めません。第2希望日の過去日チェックもありません。`withinHours()` 自体も、終了が開始より後か検証していません。
- **直し方：** お客様の送信前とスタッフの確定前に日付・時間を再検証します。営業時間外を例外承認できる運用なら、スタッフのみ理由入力付きで許可し、お客様画面で黙って通さないでください。

### 13. 「土日祝」と案内しているが、祝日を判定していない【①②】

- **行番号：** 356、562、659
- **問題：** 営業時間の判定は `getDay()` の土日だけです。平日に当たる祝日は18時開場として処理されます。
- **直し方：** 検証済みの祝日一覧を設定し、土日または祝日なら10時開場とします。祝日判定を実装しない間は、案内も **「土日 10:00〜21:00／祝日は店舗へお問い合わせください」** など実装に合わせてください。

### 14. 延長で通常料金と延長料金が両方加算される【①②】

- **行番号：** 387、566–577、852–853、863
- **問題：** 実際の終了時刻でスペース料金を再計算したうえで、延長料金を追加します。13〜16時の予約を16時30分まで利用し、延長1単位を入力すると、**4時間分61,600円＋延長10,000円＝71,600円**になります。終了時刻と延長単位の整合チェックもありません。
- **直し方：** 料金ルールを確定してください。予約時間分＋延長料という運用なら、基本料金には `r.end` を使用し、延長単位は次のように算出します。

  ```js
  const ext30 = Math.ceil(
    Math.max(0, hoursBetween(r.end, actual.end)) * 2
  );
  ```

  両方を請求する運用なら、その旨を申込前に明記します。どちらが正しい料金体系かは、このコードだけでは断定できません。

### 15. 1時間未満切り上げを料金案内に明示していない【①②】

- **行番号：** 318、356、567–572、393
- **問題：** `Math.ceil(hours)` により、2時間30分でも3時間分を請求します。「1時間 ¥15,400〜」だけでは端数の扱いが分かりません。また「お食事は¥2,000〜」ですが、基本単価を変更する入力欄はありません。
- **直し方：** 切り上げが正しいなら **「1時間15,400円（税込）。1時間未満の端数は1時間として計算します。1日上限154,000円です。」** と明記します。食事単価が可変なら、合意済み単価を予約に保存して見積・請求に使ってください。

### 16. 共有後に予約を編集しても「共有済み」が維持される【①④】

- **行番号：** 803、831–832、923–926
- **問題：** `shared` 状態でも日時・人数・プラン・メールを変更できますが、共有済み状態のままです。「送信したメールを見る」も現在の予約から再生成するため、送信時点の内容を保存できません。
- **直し方：** 共有後の変更時は **「変更内容の再共有が必要」** に戻します。送信確認時の宛先・件名・本文・日時をスナップショットとして保存し、過去の文面を上書きしないでください。

### 17. キャンセル・請求訂正・入金誤操作の訂正がない【①④】

- **行番号：** 464–472、819、842、881、937–944
- **問題：** キャンセル状態がありません。「日程を取り消す」は仮予約に戻るだけです。請求済み以降の金額訂正・再発行、誤って押した入金確認の取消もありません。「再発行になります」という説明に対応する操作がありません。
- **直し方：** 理由・日時を履歴に残すキャンセルと訂正操作を追加します。キャンセル分は予約枠・売上見込から除外し、請求訂正は旧請求書を保持して改訂版を発行します。

### 18. 将来の利用を終了・請求・入金まで進められる【①②】

- **行番号：** 843–845、935、941–943
- **問題：** 「モックなので今も入力できます」と明示され、利用前でも終了実績を確定できます。当日でも終了時刻の確認はありません。
- **直し方：** 利用終了日時までは実績確定を無効化します。過去分登録など例外操作が必要なら、理由付きの明示操作に分けます。モック用文言は削除してください。

### 19. 予約ID・請求番号が桁上がりで重複する【①④】

- **行番号：** 554–555、711
- **問題：** 下3桁／下4桁だけを読み取っています。`R-2026-999` と `R-2026-1000` がある場合、次も **`R-2026-1000`** になります。年も2026固定です。受付番号の乱数は900通りしかなく、重複確認がありません。
- **直し方：** 内部IDは `crypto.randomUUID()` を使い、表示用番号と分離します。表示番号は完全な連番部分を解析し、年別に管理してください。複数タブの採番は排他処理が必要です。受付番号もUUID由来など、十分な長さを持たせます。

### 20. 発行済み請求書の明細が固定されない【①④】

- **行番号：** 582、777、870–871、892–903、941
- **問題：** 請求書には合計だけを保存し、明細・税額・発行者情報は表示時に再計算・再取得します。後日 `PRICE` や `SHOP` を変更すると、過去請求書の内容が変わり、保存済み合計と明細合計が食い違います。
- **直し方：** 発行時に明細、単価、人数、税額、合計、宛先、発行者、振込先をまとめて保存します。発行後の表示と印刷は、そのスナップショットのみを使ってください。

### 21. 請求書の印刷・PDF保存手段がない【③④】

- **行番号：** 174–188、243–244、870–882、892–903
- **問題：** 請求書は画面内のプレビューだけです。印刷ボタン・印刷用CSSがなく、通常の印刷では管理画面も対象になります。請求書が閉じた `<details>` 内にある場合も考慮されていません。
- **直し方：** 請求書だけを表示する印刷領域と「印刷・PDF保存」ボタンを追加します。`@media print` で管理UIを除外し、改ページ・余白・表の見出しを調整してください。印刷処理の終了をメール送信完了として扱ってはいけません。

### 22. お客様画面と管理画面の分離が表示上だけ【①④】

- **行番号：** 48、594–603、951–954
- **問題：** `#apply` はナビゲーションを隠すだけです。ハッシュを外して再読み込みすると管理画面になります。共有端末では同じブラウザ内の予約・連絡先を閲覧できます。
- **直し方：** 公開受付と管理画面を分離してください。localStorage運用を続ける場合、管理端末をお客様に使わせない運用が必要です。現状のコードから「他端末の全予約が公開される」とまでは言えませんが、画面非表示はアクセス制御ではありません。

## P2：UI・安全性・使いやすさ

### 23. 通常のモバイル用viewport指定がない【③】

- **行番号：** 1–4、235–242
- **問題：** `claude:viewport-fit-sides` は通常のブラウザ向け `viewport` 指定の代わりになりません。スマホで意図した幅のメディアクエリが適用されず、縮小表示される可能性があります。また `doctype`、文字コード、ページ言語の明示もありません。
- **直し方：** 単独HTMLとして次を追加します。

  ```html
  <!doctype html>
  <html lang="ja">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport"
          content="width=device-width, initial-scale=1, viewport-fit=cover">
  ```

### 24. プラン選択のフォーカスが見えず、画面遷移後のフォーカス移動もない【③】

- **行番号：** 46、124、595–602、695、700
- **問題：** ラジオボタンが透明・幅高さ0のため、入力自体に付くフォーカス枠を視認しづらくなります。画面切替はスクロールするだけで、見出しへのフォーカス移動がありません。エラーも項目との関連付けがありません。
- **直し方：**

  ```css
  .plan-opt:has(input:focus-visible) {
    outline: 2px solid var(--accent);
    outline-offset: 2px;
  }
  ```

  画面切替後は `tabindex="-1"` を付けた見出しにフォーカスを移します。エラー要約は `role="alert"`、対象入力は `aria-invalid="true"` と `aria-describedby` で関連付けてください。確認同意のエラーは「入力してください」ではなく **「確認のうえ、チェックを入れてください」** とします。

### 25. 追加項目の削除→追加でIDが重複する【①③】

- **行番号：** 860、932–934
- **問題：** 新しい行のIDに `box.children.length` を使っています。0・1の2行から0を削除して追加すると、`x-l-1` と `x-a-1` が重複します。ラベルが別の行の入力欄を指す状態になります。
- **直し方：** 件数ではなく単調増加カウンターまたはUUIDを使います。

  ```js
  const key = crypto.randomUUID();
  box.insertAdjacentHTML('beforeend', extraRow({}, key));
  ```

### 26. ダークモードで請求ボタンと請求書内の文字色が不整合【③】

- **行番号：** 18、24、93、174、229、896–898
- **問題：** `.btn-money` はダークモードでも文字が白固定で、背景は明るい金色 `#dcb860` です。請求書は白背景固定なのに、内部の `.muted` はダークモード用の明るい文字色を引き継ぎます。
- **直し方：** ボタン用前景色をテーマ別に定義し、請求書内の文字色は白背景用に固定します。

  ```css
  .btn-money { color: var(--money-fg); }
  ```

| ライト：warn／warn-soft | 約4.81:1 |
| ダーク：muted／surface | 約6.67:1 |
| ダーク：warn／warn-soft | 約7.56:1 |

一方、`.card.locked { opacity:.55 }`では補足文字がライト約2.34:1、ダーク約2.93:1まで下がります。未着手カードの説明は、読める必要がある情報です。

**直し方：**

```css
.card.locked {
  opacity: 1;
  background: var(--surface-2);
  box-shadow: none;
}
```

色の意味も統一します。

- `accent`：現在の主要操作・選択
- `money`：金額・請求書発行
- `warn`：相談や注意が必要
- `danger`：入力エラー・破壊的操作
- `ok`：確認できた完了

必須表示までwarn色にする必要はなく、通常の文字色＋「必須」で区別できます。

## 4回目（UI/UX 反映後の確認）

静的コード確認です。概ね反映されていますが、以下が残っています（行番号はすべて `rental-space-tool.html`）。

**1) 反映漏れ・矛盾**

- **L299：ヘッダーは2段のまま。** `.nav{width:100%}` によりブランドとナビが別段になります。
- **L314・L907–914：カードの状態バッジ位置。** `justify-self:end` だけでは日時の右に移らず、金額の次の行に配置されます。`grid-row:1; grid-column:2` などの明示が必要です。
- **L1376・L1381：エラー対応が未統一。** 実績入力はトーストのみ、請求先メールはメッセージのみで、赤枠・フォーカス移動がありません。

**2) 残るP0/P1：P0なし、P1は2件**

- **P1｜L1–2：通常のviewport指定がない。** 単体HTMLとしてスマホで開くと、375px向けCSSが適用されない可能性があります。`<meta name="viewport" content="width=device-width, initial-scale=1">` を追加してください。
- **P1｜L654・L693–695・L922：共有先でメール申込にならない。** 店舗メールはスタッフ端末のlocalStorageにしか保存されず、共有URLにも引き継がれません。別端末のお客様には電話申込が表示されます。公開フォームでも店舗メールを取得できるようにし、別端末で確認が必要です。

**3) 文言**

- **L1242：**「共有済み」→「メール作成済み」。
- **L1390：**「請求済みに戻しました」→「請求書発行済みに戻しました」。
- **L567：**「空欄だと請求書を発行できません」は対象が曖昧。実際の必須条件に合わせ「発行者名・振込先は必須です」に。
- **L1098：** 電話時の「受付番号をお伝えください」は、通常の別端末利用では店舗側が番号で照会できません。「ご希望日時・人数・お名前をお伝えください」が適切です。
