# bokashi 定例会議フロー

コンサルティング定例会議を5つのフェーズで進行する対話型ワークフロー。
各フェーズ完了後にユーザーが「次へ」と言うまで待機する。

## 共通ルール

**全フェーズの完了報告時に、以下の2つのURLを必ず提示すること:**
- **Notionページ**: 当該会議のNotionページURL
- **ダッシュボード**: https://bokashi-dashboard.streamlit.app

## 全体の流れ

```
Phase 1: データ取り込み ──→ Phase 2: AI分析レポート ──→ Phase 3: 会議実施（人間）
                                                              │
Phase 5: 総合フィードバック ←── Phase 4: 議事録構造化 ←──────┘
```

## 途中参加の判定

ユーザーの発話から、どのフェーズから開始するか判定する:
- 「会議フロー」「MTG」「定例」→ Phase 1 から開始
- 「会議の準備」「分析して」→ Phase 2 から（データ確認後）
- 「議事録更新」「議事録を構造化」「文字起こしを処理」→ Phase 4 から
- 「フィードバック」「総合分析」→ Phase 5 から
- NotionのURLが添えられている場合 → そのページを対象にPhase 4 or 5

## Phase 1: 売上データ取り込み

Google Driveから最新の売上CSVを取得してローカルに保存する。

### 手順

1. Google Drive MCP の `search_files` で売上フォルダ（parentId: `1Ligr0RnQOo7aPB9iZ2YMS0CefsgGHuBC`）を検索
2. ファイル一覧の `modifiedTime` を確認し、**会議日の直前データがあるか**を自動チェック
   - 最新CSVの日付が会議日の1週間以上前 → 警告を出す:
     「最新の売上データは {日付} 時点です。舜さんにスマレジからの最新CSVエクスポートを依頼してください。前回データで分析を進めますか？」
   - ユーザーが「進めて」→ 既存データで Phase 2 へ
   - ユーザーが「待つ」→ 一旦待機
3. 新規・更新CSVを `download_file_content` で取得
4. ローカル `data/sales/` に保存（既存ファイルと重複チェック）
5. 取り込み結果のサマリーを表示:
   - 取り込んだファイル名・期間
   - 前回取り込みからの差分

### 完了条件
- 売上データがローカルに保存されている状態
- ユーザーに「Phase 1 完了。『次へ』で分析レポートを作成します」と伝える

## Phase 2: 会議前AI分析レポート

最新の売上データと前回議事録を突き合わせ、会議の論点をNotionページに書き込む。

### 鉄則: 数値は必ずコードから生成する

**売上・客数・曜日などの数値をNotionブロックに書く際、会話テキストや前セッションの要約から転記してはならない。**
必ず `app/data_loader.py` の関数でCSVから算出し、その戻り値からNotionブロックを組み立てること。

使うべき関数:
- `load_daily()` → `validate_daily()` で読み込み＋検証
- `build_summary_table()` で同期間比較テーブルを自動生成
- `build_weekly_table()` で日別テーブルを自動生成（曜日は日付から自動算出）
- `compare_same_period()` で月間比較
- `load_product()`, `load_department()`, `load_hourly()`, `load_weekday()` 等

**禁止事項:**
- `csv.reader` や生の `pd.read_csv` による手書きパース
- 前セッション要約の数値を転記してNotionに書くこと
- 曜日・日付の手動入力（必ず `datetime` から算出）

### タスク台帳（`data/tasks.json` / `app/task_ledger.py`）— 2026-09-08 導入

アクションアイテムは会議をまたいで **台帳** で管理する。議事録mdからの再集計はしない。

- 状態は `進行中 / 保留 / 完了 / 取下` の4種。**完了・取下は翌週以降のレポートに表示しない**（`task_ledger.open_tasks()`）
- Notionには `task_ledger.todo_blocks()` で **to_do（チェックボックス）ブロック** として出力。先頭の `#id` が台帳キー。
  状態タグ（🔄 進行中 / ⏸ 保留）を色付きで表示し、**チェックを入れる＝完了**
- Phase 4 で `task_ledger.sync_from_notion(page)` を呼び、チェック済み to_do を台帳で「完了」にする。
  会議で新たに決まったアクションは `task_ledger.add()` で追加し、残ったタスクは `bump_carry()` で持ち越し回数+1
- `carry`（持ち越し回数）が3以上 → 停滞タスク、2 → 要判断、1 → 前回発生分

### レポート生成は `app/meeting_report.py` で行う（フォーマット固定）

**毎回同じフォーマットを維持する（オーナー指示 2026-09-08）。** ページ構成・テーブル・タスクの出し方は `meeting_report.py` に固定されており、
会議ごとに変わるのは `docs/meeting-notes/ctx/YYYY-MM-DD.json`（前回の要点・注目ポイントの文章・提案・論点・AIフィードバック文）だけ。

```
python app/meeting_report.py --ctx docs/meeting-notes/ctx/2026-09-08.json --keys     # 文章で使える {キー} 一覧
python app/meeting_report.py --ctx docs/meeting-notes/ctx/2026-09-08.json --dry      # ブロック数確認
python app/meeting_report.py --ctx docs/meeting-notes/ctx/2026-09-08.json --rebuild  # ページを全削除して書き直し
```

- ctx の文章中の数値は必ず `{daily_y}` `{sh_ランチ:.1f}` のようなキーで埋め込む（数値の手打ち禁止）。前回の ctx をコピーして文章を書き換えるのが最短
- 担当者名は `舜 / 慎也 / 準 / とし`（オーナーは「準」。「純」は誤り）

### 手順

1. `app/notion_writer.create_meeting_page()` でNotionに新規会議ページを作成
2. `app/data_loader.load_daily()` + `validate_daily()` で売上データを読み込み・検証
   - 警告が出たらユーザーに報告してから分析を進める
3. `task_ledger.open_tasks()` で未完了タスクを取得し、`carry` で分類:
   - **3回以上持ち越し** → 自動棚卸し対象。AI側が「取り下げ推奨 / LINEノート統合 / 保留 / 継続」を明示判断する
   - **2回持ち越し** → 「要判断」として警告
   - **1回（前回発生分）** → 前回の振り返りセクションでチェックリスト表示
   - `docs/meeting-notes/` の直近議事録からは、前回の決定事項と「総合AIフィードバック」の実行状況だけを読む
4. **タスク棚卸しセクションはページ後半に配置する**（オーナー指示 2026-09-08: 会議はまず前回の振り返りと数字のダイジェストから入る）:
   - 3回以上持ち越し → to_do ブロック＋AI判断。根拠はトグルに格納
   - 担当者別タスク負荷テーブル: 未完了タスク数を担当者別に表示し、`bokashi.yaml` の `analysis.max_tasks_per_person`（デフォルト10）件を超える担当者には警告を出す。担当者ごとのトグルで具体的なタスク一覧を展開できるようにする
5. 売上データを分析（**全てdata_loaderの関数経由**）:
   - 月別売上推移（全月の合計売上テーブル）
   - `build_summary_table()` で同期間比較サマリー
   - `build_weekly_table()` で直近1週間の日別テーブル
   - 注目ポイント・分析（ポジティブ / 要注意）
   - 以下の詳細データは**Notionのtoggleブロック内に格納**（会議中に必要な時だけ展開する2層構造）:
     - `load_hourly()` で時間帯別構成
     - `load_weekday()` で曜日別構成
     - `load_department()` で部門別構成
     - `load_product()` で商品別ランキング
     - `load_customer()` で顧客動向（新規/リピーター）
6. 前回アクションアイテムの進捗確認テーブルを作成
7. **新プラン・改善提案セクションを作成**:
   - 売上データのトレンドから見えるチャンス・リスク
   - 前回フィードバックの提案のうち未着手のものを再提示
   - 季節・時期に応じた新しい施策アイデア
8. **会議タイムテーブルの自動生成**:
   - 棚卸し件数×2分 ＋ 重点議題数×10分 ＋ アクション確認10分 ＋ バッファ10分 で所要時間を概算
   - 60分を超える場合は「議題の絞り込みを推奨」と警告
   - Notionページ冒頭のcalloutブロックに推奨タイムテーブルを配置
9. 「本日の会議で議論すべきポイント」を生成（売上データ×前回課題×停滞タスクから導出）
10. 上記をNotionページに書き込み（`append_blocks` で構造化）
11. ページURLとダッシュボードURLをユーザーに共有

### 分析レポートの構成（Notion出力順序）

```
[callout] 推奨タイムテーブル（自動計算）  ← 会議の進行ガイド
[callout] タスクの使い方（チェック＝完了、翌週非表示）
---
1️⃣ 前回会議の振り返り
   前回の決定事項と今回の確認ポイント（テーブル）
   前回発生アクションのチェック（to_do、carry=1）
---
2️⃣ 数字ダイジェスト
   [callout] 1行サマリー（日販・客数・客単価・主要変化）
   月別売上推移（全月テーブル）
   売上サマリー（同期間比較テーブル＋前月差分テーブル）
   直近1週間の勢い（前週比較はトグル）
   注目ポイント（ポジティブ / 要注意）
   [toggle] 📊 詳細データ  ← 必要な時だけ展開
     ├ 時間帯別 / 曜日別 / 部門別 / 商品別ランキング / 顧客動向
---
3️⃣ 提案と本日の論点
   着地見通し（シナリオ表）・優先施策・（必要なら）試算セクション・本日の論点
---
4️⃣ 🤖 AI売上フィードバック（6観点）
---
5️⃣ 【後半】タスク棚卸しと担当者別負荷
   ⚠️ 3回以上持ち越し（to_do＋AI判断、根拠はトグル）
   🟡 2回持ち越し（to_do）
   👥 担当者別タスク負荷（テーブル＋担当者別トグル）
---
文字起こし全文（貼り付け欄）
```

### 完了条件
- Notionページにレポートが書き込まれている
- Streamlitダッシュボードの公開URLを提示する
- 「Phase 2 完了。Notionページ: {URL}。ダッシュボード: https://bokashi-dashboard.streamlit.app 。会議で活用してください。会議後に『次へ』で議事録の構造化に進みます」

## Phase 4: 議事録構造化

Notionページに貼られた文字起こしを、構造化議事録に変換する。

### 手順

1. `app/notion_reader.fetch_page()` でNotionページの全テキストを取得
   - ブロックに `has_children=True` がある場合、再帰的に子ブロックも取得
2. 名前マッピングを適用（`memory/reference_name_mapping.md` 参照）:
   - 駿/しゅん/シュン → 舜（店長）
   - 椎名/しいな/シイナ → 慎也（コンサルタント）
   - Speaker 1, Speaker 2 等 → 文脈から推定して割り当て
3. 既存ブロックを全削除（`delete_blocks`）
4. 構造化議事録を上部に、文字起こし原文をトグル（折りたたみ）に格納して書き込み

### 構造化議事録のテンプレート

```
[コールアウト] YYYY-MM-DD 定例会議（構造化議事録 — AI分析済み）
参加者 / 所要時間
---
## 議題・要点
### 1. 売上状況（← 必ず最初に配置。売上サマリーテーブル + 分析）
### 2. 時間帯・曜日別動向（テーブル付き）
### 3. 部門別売上構成（テーブル付き）
### 4〜. その他の議題（メニュー、オペ、人事、契約等）
  - 要点（箇条書き）
  - [コールアウト] 重要な決定事項
---
## 決定事項・アクション（テーブル: #, カテゴリ, アクション, 担当, 期限）
---
## 前回アクション進捗（テーブル: #, アクション, 状況）
---
## 数値メモ
---
## 総合AIフィードバック（Phase 5の内容をここに統合）
---
[トグル] 文字起こし全文（クリックで展開）
```

**重要: 売上データの分析（サマリーテーブル・時間帯・曜日・部門）は必ず議題の最上部に配置する。**
これは5/27以降の定例フォーマットとして固定。

5. ローカル `docs/meeting-notes/YYYY-MM-DD.md` にも保存（frontmatter付き）
6. **タスク台帳を更新する**（削除前に必ず実行。to_do のチェック状態は文字起こしと一緒に消えるため）:
   - `task_ledger.sync_from_notion(page, meeting_date)` → チェック済み to_do を「完了」に
   - 議事録の「決定事項・アクション」から新規タスクを `task_ledger.add()` で追加（担当・期限・カテゴリ付き）
   - 会議で「取り下げ」と決まったものは `set_status(id, "取下")`
   - 完了・取下は `archive_done()` で台帳から**削除**し `data/tasks_archive.json` に移す（`sync_from_notion()` が自動で呼ぶ）
   - 最後に `bump_carry()` で残タスクの持ち越し回数を+1し `save()`
   - 構造化議事録の「決定事項・アクション」テーブルには台帳の `#id` を付ける

### ローカル保存のフォーマット

```markdown
---
date: YYYY-MM-DD
duration: 約X時間XX分
participants: 参加者名
source: Notion URL
---
# YYYY-MM-DD 定例会議
（以下、Notionと同じ構造）
```

### 完了条件
- Notionページが構造化議事録に書き換わっている
- ローカルにmdファイルが保存されている
- 以下のURLを必ず提示する:
  - Notionページ: {URL}
  - ダッシュボード: https://bokashi-dashboard.streamlit.app
- 「Phase 4 完了。決定事項・アクションアイテムを報告:」のあとに主要な決定事項を列挙
- 「『次へ』で総合フィードバックを生成します」

## Phase 5: 総合AIフィードバック

売上データと議事録の内容を統合し、経営視点での本質的課題と提案を生成する。

### 手順

1. Phase 4で作成した構造化議事録を読み込み
2. 最新の売上データを再度参照
3. 以下の観点で総合分析を行う:

### 分析の観点

**a. 本質的課題の抽出**
会議で議論された内容の中から、表面的な症状ではなく根本原因を特定する。
例: 「スイーツの売上が落ちた」→ メニュー変更の影響? 季節要因? オペレーション負荷による品質低下?

**b. 未解決事項の指摘**
会議で結論が出なかった、またはアクションアイテムが曖昧な議題を指摘する。
担当者・期限・具体的な成果物が不明確なものを洗い出す。

**c. 数値に基づく提案**
売上データのトレンドから、次のアクションを具体的に提案する。
- 伸びている領域: さらに投資すべきか
- 落ちている領域: 原因と対策
- 新しい機会: データから見えるチャンス

**d. 事業間シナジーの視点**
bokashi単体ではなく、親会社の他事業（農園、福祉、サウナ、バー等）との連携可能性を指摘する。
`../../02_synergy/` の情報も参照する。

**e. 次回会議までのマイルストーン提案**
アクションアイテムの優先順位を整理し、次回会議までに達成すべき中間目標を提案する。

### 出力先

4. Notionページの末尾に「総合AIフィードバック」セクションとして追記（`append_blocks`）
5. 構成:

```
---
## 総合AIフィードバック
### 本質的課題
### 未解決事項・要確認
### データに基づく提案
### 事業間シナジーの可能性
### 次回（MM/DD）までのマイルストーン
---
[コールアウト] このフィードバックはAIによる分析です。現場の感覚と突き合わせて活用してください。
```

### 完了条件
- Notionページにフィードバックが追記されている
- ユーザーに主要なフィードバックポイントを口頭で報告
- 以下のURLを必ず提示する:
  - Notionページ: {URL}
  - ダッシュボード: https://bokashi-dashboard.streamlit.app
- 「会議フロー完了。お疲れ様でした！」

## 運用上の注意

- **Notion APIの制限**: 1ブロック内のrich_textは2000文字まで。長いテキストは分割する
- **ブロック削除**: 一度に大量のブロックを削除するとレート制限に当たる可能性がある。エラー時はリトライ
- **データの鮮度**: Phase 1でデータの鮮度を必ずチェックする。古いデータでの分析はその旨を明記する
- **名前マッピング**: 新しい参加者が増えた場合、`memory/reference_name_mapping.md` に追記する
- **トグルの活用**: 長いテキスト（文字起こし等）は必ずトグルに格納し、ページの可読性を保つ
